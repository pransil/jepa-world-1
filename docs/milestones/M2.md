# M2: Data pipeline and baselines

- **Completed:** 2026-11-17   **PRs:** (this PR)

## Built

[`jepa_world/data/DESIGN.md`](../../jepa_world/data/DESIGN.md) has the shapes, decisions and
seams.

| module | role |
|---|---|
| `data/splits.py` | terrain-seed splits from `data.splits`: dev 0–9, train 1000–1499, test 100000–100049, 4 balls each. Test ball seeds (1000–1003) are disjoint from train's (0–3). `LeakageError`, `check_split_config` |
| `data/build.py` | one write-once dataset per split through `paths.build_dataset_once`, keyed on (sim cfg, the split's seeds, `format_version`). M1 episode files, plus `manifest.json` (seeds, terrain hash) and `meta.json` (`run_metadata`, timing). The CLI takes the GPU lock |
| `data/dataset.py` | `load_split` (on-disk leakage checks, then the whole split in RAM as uint8), `valid_starts`, `window_frames` (refuses windows outside the episode), `batches`: (B, C+k_max, 3, S, S) float32, uniform over windows, seeded |
| `baselines.py` | persistence; constant velocity from the true v(t); constant velocity from the context's finite difference (C ≥ 2). `evaluate`: error per k on one shared window set, ratio to persistence, split by out-of-view at t+k |
| `eval.py` | `--baselines` mode, which writes a run dir. `--run` stays the M6 stub |
| `train.py` | `data.source: episodes` reads `data.split` (dev or train only; test is refused). `main()` loads the split before taking the GPU lock |

  - no on-disk ball-seed check;
  - finite-difference baseline kept with C = 1;
  - view split read at t instead of t+k.

Constant velocity beats persistence up to k = 10 and loses at k = 20. Over 1.3 s the terrain
turns the ball (slopes, walls, settling), so extrapolating straight overshoots. The far
horizons are where knowing the terrain has to pay off.

Out of view at t+k, on test: 161–202 of 7400 windows (2.2–2.7%). The errors there are 2–4×
larger. For persistence, in view / out of view: k = 1 0.129 / 0.328, k = 5 0.559 / 1.500,
k = 20 1.652 / 3.893 m. Per-baseline numbers are under `mean_error_m_by_view_at_t_plus_k` in
`baselines.json`.

**Dev split** (debugging only, never a generalisation claim, SPEC §7.3): run
`runs/20261118T051756Z-worktree-wt-m2-data-baselines-dev-76a540`. 40 episodes, 1480 windows.
Persistence at k = 1 / 5 / 20 is 0.134 / 0.587 / 1.819 m. Constant velocity's ratios are 0.157 /
0.521 / 1.079.

**End-to-end smoke** (loader → JEPA on MPS, near stage, B = 32, 20 steps, dev split): run
`runs/20261118T051811Z-worktree-wt-m2-data-m2-dev-smoke-e757b1`. Every term is logged at every
step, and `loss/total` went 186.1 → 88.4. This shows only that the pipeline runs. The
"loss decreases on the dev set" test belongs to M3.

## Open issues / deferred

- **Simulator-aware baseline → M6.** It needs a `sim/` entry point that starts from a
  mid-episode state. That is recorded as an M2 → sim/ handshake in `docs/process/LANES.md`
  ([decision](../decisions/2026-11-17-m2-baseline-scope.md)).
- **Cross-config leakage → M6.** The on-disk check sees only the current config's splits. M6's
  model eval must compare the run's `config.yaml` splits with the eval config (data/DESIGN.md).
- **M6 must score the model on the baselines' windows**, t ∈ [C−1, T−1−max(model.horizons)],
  even for a near-only model (data/DESIGN.md).
- **`eval --baselines` decodes frames it doesn't use.** That is at most 200 episodes (about
  150 MB) for dev or test. A positions-only reader would duplicate `sim/io`'s format, so it would
  need a `frames=False` option in `sim.io.load_episode`, which the sim/ owner would have to add.
- **Train split in RAM:** 2000 × 60 × 3 × 64 × 64 uint8 ≈ 1.5 GB per training process. Revisit
  (memory-map a consolidated array) if the dataset grows past a few GB.
- `jepa_world/models/DESIGN.md` line 11 still says "Until M2 lands". That file is in the M4 lane,
  so it was left alone here and flagged to the orchestrator.
