## Built

[`jepa_world/models/DESIGN.md`](../../jepa_world/models/DESIGN.md) has the shapes, decisions and
seams. Everything below was built in PR #4.

| module | role |
|---|---|
| `models/unet.py` | U-Net context encoder: three levels L1 (64ch @ 64), L2 (128 @ 32), L3 (256 @ 8), GroupNorm, 3×3 stride-2 downsampling, no buffers |
| `models/heads.py` | one predictor head per horizon, reading its level. A learned k-vector and an action slot (zeros in v1) are broadcast over positions |
| `models/jepa.py` | `JEPA`: the context encoder, an EMA target encoder that encodes the 4-frame stack ending at t+k (no_grad, detached), and the near heads. `compute_losses`: squared-L2 latent loss per k, plus the VICReg variance guard |
| `train.py` | AdamW over trainable parameters only. EMA runs after `opt.step()`. Every term is logged at every step to `metrics.jsonl` and TensorBoard. Checkpoints, a run dir, the GPU lock |
| `bench.py` | the SPEC §11 L1-head benchmark |

**The dev-set test** builds the real dev split (10 terrains × 4 balls, rendered by MuJoCo) into
its own tmp artifact root. It then trains `configs/m3_near_dev.yaml` (near stage, SPEC shapes,
the current `base.yaml` loss) through M2's loader and `train.run`, on CPU, with B = 4 for 250
steps. It compares the mean over the last 25 steps against the mean over the first 25, on the
near horizons k = 1..5, and asserts:
- every step is logged, and every value is finite;
- **scale-free error** (the mean of `relerr/k`: error relative to predicting the batch-mean
  target, M4's `relative_error`): last < 0.5 × first, and last < 1.0, meaning better than
  predicting the batch-mean target;
- **raw latent loss** (Σ_k `loss/k`, SPEC's literal claim): last < 0.8 × first;
- the mean `emb_std/L1` over the last 25 steps is above 0.1, so the drop isn't collapse.

Why `relerr` leads: the raw loss is squared L2 on raw embeddings, so it scales with the embedding
spread, and the variance guard grows that spread. Under M4's guard settings
([guard sum, w_var 25](../decisions/2026-11-17-far-collapse-guard-sum.md)) the spread doubles
over this run. A raw-loss margin would therefore measure the guard as much as the predictor.

Measured on this setup, under the merged defaults:
- `relerr`: 2.42 → 0.38 (ratio 0.16);
- raw latent: 110 → 31 (ratio 0.29);
- `emb_std/L1`: 0.32 → 0.64.

It was seen to fail: rerun with `train.lr=0` and nothing else changed, it fails (PR body).

Also covered in PR #4:
- leakage at the model boundary: `test_context_ignores_future_frames`,
  `test_target_k_ignores_frames_after_t_plus_k`;
- determinism: `test_same_seed_gives_identical_losses`;
- every term logged at every step, even across a crash;
- MPS at SPEC shapes is finite, with no CPU fallback (`mps` tier).

M2 adds the data-side leakage tests (docs/milestones/M2.md).

## Measured

**The L1-head benchmark** (MPS, fp32, B = 32, SPEC shapes; [decision file](../decisions/2026-11-17-l1-head-width.md)):
- the chosen head, 32 wide with 3×3 convs, takes 75–93 ms per full train step and 40–49 ms for
  the 5 heads' forward and backward;
- MPS driver memory is 2.1 GB;
- no op fell back to CPU.

The runs are `runs/20261118T021043Z-…-bench-l1-heads-a5add4` and
`runs/20261118T042046Z-…-bench-l1-heads-a92e58`.

**Near heads on the dev split, MPS, current defaults:**
`uv run python -m jepa_world.train --config configs/m3_near_dev.yaml` at commit 65d9cca (clean,
with M4's guard sum and w_var 25). B = 32, 600 steps, run
`runs/20261118T055916Z-worktree-wt-gt-batches-m3-m3-near-dev-790df2/metrics.jsonl`.

| step | 1 | 50 | 100 | 200 | 300 | 400 | 500 | 600 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| near latent Σ_k loss/k | 185.4 | 62.7 | 50.9 | 58.5 | 41.1 | 40.7 | 37.2 | 29.9 |
| mean `relerr/k`, k = 1..5 | 3.09 | 0.65 | 0.46 | 0.40 | 0.22 | 0.18 | 0.14 | 0.10 |
| `emb_std/L1` | 0.29 | 0.69 | 0.73 | 0.81 | 0.92 | 0.97 | 1.09 | 1.13 |
| `loss/var` | 46.2 | 23.9 | 20.5 | 14.8 | 7.4 | 4.7 | 1.6 | 1.0 |

- Mean over the first and last 25 steps: `relerr` 1.82 → 0.15 (ratio 0.085), raw latent
  111 → 47 (ratio 0.42), `emb_std/L1` 0.50 → 1.10. Every value is finite.
- The last 25 steps per horizon, `relerr`: k1 0.07 < k2 0.10 < k3 0.15 < k4 0.20 < k5 0.25. Raw
  `loss/k` has the same order (4.2 … 15.3). Farther is harder, as expected.

**The same run under M3's original guard** (mean reduction, w_var 1; commit 2522fe7, before M4
merged; run `runs/20261118T054850Z-worktree-wt-gt-batches-m3-m3-near-dev-c74be0`) went
106.1 → 21.5 in raw latent loss. That loss bottomed out around steps 300–400 and rose again as
`emb_std/L1` grew from 0.38 to 0.46. That run predates `relerr`. It is the observation that made
raw loss the wrong criterion, and M4's `relerr` is the scale-free readout that replaces it.

**Context: M4's dev runs** (near and far stages, 600 steps, B = 32, `runs/*wt-m4-far-heads-dev-*`)
give near latent from the first 20 steps to the last 20:

| run | near latent | `emb_std/L1` |
|---|---|---|
| `dev-baseline-a710ab` | 113 → 12 | 0.29 → 0.33 |
| `dev-layernorm-3c5d77` | 234 → 31 | |
| `dev-guardsum-df9b23` | 118 → 73 | 0.29 → 1.12 |
| `dev-both-ecc99d` | 238 → 53 | |

The guard variant moves the embedding to unit scale, and its raw latent loss is correspondingly
larger. Those are M4's runs, cited only as context. The SPEC test above is this milestone's own.

## Open issues / deferred

- **Raw latent loss depends on embedding scale** (above). M4's `relerr/k` is the scale-free
  readout, and the dev-set test leads with it. Any comparison of raw `loss/k` across guard
  settings needs the same care.
- The L2 and L3 encoder stages get no gradient in a near-only run. They start training with M4's
  far heads.
- The L1 receptive field (9×9 px with 3×3 heads) is smaller than the ball's travel by k = 5
  (head-width decision, SPEC §9.6).
- Dev numbers are for debugging only (SPEC §7.3). Held-out evaluation is M6's job.
