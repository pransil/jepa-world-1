## Hypothesis and rules (pre-registered)
**The top-down terms make context L3 keep finer information about the ball, which lowers the
goal head's k = 20 position error.**

- **Deciding metric:** goal-head position error at **k = 20** ÷ persistence, on the **test** split,
  at step 48,000 (`experiments/m7_ablation_check.py --deciding goal_k20`). Reference:
  **0.3288 / 0.3312**.
- **Verdict:**
  - **supported** if both top-down seeds are below both reference seeds (both under 0.3288);
  - **refuted** otherwise: within the seed spread, or worse (M7-plan §4).
- **Guards: a "supported" counts only if these also hold.**
  - **Latent heads not worse.** On **dev**, `experiments/latent_relerr.py --split dev` (200 batches,
    CPU) gives `relerr` at k1–k5, k10 and k20. Under the both-seeds rule, none may be **worse**
    than the reference. The reference runs are scored the same way.
  - **Training-sanity gates:** the reference's A1–A5 thresholds, applied by the scorer:
    - every term finite;
    - `emb_std` never below 50% of its step-2,000 value;
    - far `logvar` averaging −3 or more over the last 500 steps, and never below −8;
    - `pix_share` within 1e-4 of 0.10;
    - `w_goal_eff` = 0.5 / 256.

    A run that fails a gate is reported, and not used for a verdict.
- **Reported, no prediction:**
  - goal head k = 1–10 against the reference, with the same rule;
  - dev;
  - const-velocity and the mean-parameter simulator;
  - calibration and out-of-view behaviour;
  - **probes:** `pos_cam` at L2 and L3, the mechanism's direct readout. Also the hidden
    parameters (radius, friction, restitution) at L3, read from the eval JSON's `by_level`, and
    pooled;
  - the top-down terms' own `relerr/td/k10` and `relerr/td/k20`, and the far `logvar`;
  - step time against the reference.

## Procedure
One job at a time, each only with no other project python job (`tools/gpu-status.sh`) and ≥ 10 GB
free. `latent_relerr.py` runs on CPU, alongside training only with ≥ 10 GB free and never alongside
an eval. The worktree stays clean throughout.

2. Eval s0: `uv run python -m jepa_world.eval --run <dir> --split test --split dev`.
3. Train s1: the same, with `--set seed=1 --name m7-top-down-s1`. Then eval s1.
4. Dev latent scores, for both arm runs and both reference runs:
   `uv run python experiments/latent_relerr.py --run <dir> --split dev`.
5. Score: `uv run python experiments/m7_ablation_check.py --arm <s0> --arm <s1> --ref <0f2411> --ref <ada237> --deciding goal_k20`.

**Budget:** about 35% slower per step than the reference (M4's synthetic bench: 201 ms against
146–151 ms). That is about 2.5 h per seed, ≈ 5–5.5 GPU-h with the evals. Plus four CPU latent scores

## Conclusion
**Refuted.** With top-down on, the goal head's k = 20 test error ÷ persistence is 0.3446 / 0.3545,
against 0.3288 / 0.3312, so both seeds are worse. It is worse at every horizon (k = 1 +20%), and dev
agrees.

**The mechanism didn't appear:**
- L3's ball-position probe is within the seed spread, and L2's is worse in both seeds.
- The latent heads were slightly better at k = 1–5 on dev, and the top-down branches learn their
  targets. So the loss did what it was built to do. That didn't carry over to the position readout.

**What the training curves add (description, not a test):**
- **The top-down runs escaped persistence sooner.** Training-batch k1 `goalratio` over steps
  12,001–16,000 was 0.711 / 0.774, against 0.927 / 0.925.
- **They then plateaued higher.** Over 44,001–48,000 it was 0.271 / 0.269, against 0.227 / 0.263.
  That is the same shape §2's skips-off runs showed.
- **The far heads became more confident:** k20 `logvar` −0.29 / −0.26 against −0.04 / −0.04 on
  training batches, and lower on dev too.
- **L3's spread fell slightly:** `emb_std/L3` 1.848 / 1.855 on dev, against 1.910 / 1.895. That is
  well above the collapse gate.

**Cost:** about a third more time per step.

## Next
- **No change to the defaults.** `model.top_down` stays `false`.
- **For M7's write-up:**
  - top-down targets made the latent heads a little better and the goal head worse at every
    horizon;
  - better latent prediction did not mean better position readout.
- **Not proposed: a lower `loss.w_td`.** 0.5 was never varied, so a smaller weight is the cheapest
  next test if the user wants to pursue top-down. Nothing here points to it helping.
